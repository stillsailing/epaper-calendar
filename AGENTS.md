# Project context

- Hardware is ESP32-L + DESPI-C73 + GDEP073E01, using classic ESP32 / WEMOS LOLIN32. Do not apply ESP32E6-E01 or ESP32-S3 assumptions.
- The intended product is a battery-powered offline calendar. Generate pages locally on the Mac (`scripts/generate_pages.py`, `scripts/pack_calendar.py`); do not introduce a deployed backend or Wi-Fi without a change in requirements.
- Main sketch: `firmware/epaper_calendar/epaper_calendar.ino`. Preserve the Arduino folder/file naming relationship, and keep `partitions.csv` in the sketch folder; the core picks it up automatically.
- Build with `scripts/compile.sh`. FQBN is `esp32:esp32:lolin32`; the initialization baseline uses ESP32 core 3.3.11.
- The build script must remain build-only. Uploading firmware, `scripts/flash_data.sh` and `scripts/set_rtc.py` program connected hardware; run them only when requested as part of the task.
- Vendor driver files and `image.h` match the preserved ZIP. `image.h` is kept but no longer included by the sketch. Keep changes narrow and document any driver changes against the source and hardware documentation.
- Without button presses, the firmware refreshes at most once per date (plus once after power-on or reset); button refreshes are debounced and settled before drawing. Every refresh ends with the vendor power-off routine. In DS3231 mode the ESP32 then deep-sleeps until shortly after the next local midnight, a browsing timeout, or a wake button. Keep refresh frequency and display power management explicit. The panel deep-sleep command (0x07) remains disabled as in the vendor code.
- Pages live in the `calendar` flash partition (4 MB flash layout; `app0` size matches lolin32's `upload.maximum_size`). The blob format is defined jointly by `scripts/pack_calendar.py` and `calendar_store.cpp` (keys: YYYYMMDD day pages, YYYYMM00 month views, 0 fallback); change both together and bump the format version.
- The clock is an external DS3231 on I2C, chosen by the user but not yet purchased. Without it the firmware falls back to an internal-clock mode: it stays awake (no deep sleep), counts time with `esp_timer`, accepts `SET` over serial at any time, and requires continuous USB power; any reset loses the time. The 4 MB flash is confirmed (`esptool flash-id`); GPIO21/22 is still an assumption. On the tested board (CH340) opening the serial port on macOS resets the ESP32, so in internal-clock mode any port open erases the time; `set_rtc.py` keeps the port open until the refresh finishes for that reason and always sends Asia/Shanghai time. The board has no SD slot in this design; do not assume other storage or clock hardware.
- Buttons (active low, internal pull-ups), left to right on the enclosure: wake GPIO32 (the only deep-sleep wake source, ext0; no diodes by the user's choice), previous month 33, previous day 25, today 26, next day 4, next month 16, month view 17 (toggles between the day page and the month page; while streaming the page the firmware recolors today's cell into a red rounded block with white text, using `kMonthGrid*`, which must match `MONTH_GRID_*` in `generate_pages.py`, as a test checks). In DS3231 mode the chip stays awake 30 s after the wake key. Browsing waits 1.5 s after the last press before drawing, refuses dates without a page, and returns to today after 2 minutes. Not yet tested on hardware.
- Build success is not hardware validation. The firmware has booted on the device in internal-clock mode, read pages from flash and completed refreshes (BUSY returned); the user confirmed orientation and colors look right. DS3231 mode and deep sleep are untested. Upload at 460800 baud: 921600 fails through the user's USB hub. Vendor BUSY waits have no timeout; a 120 s task watchdog resets the chip and the next boot skips the panel until the next day. That limits battery drain only; do not claim runtime recovery or thermal protection exists.
- `preview/calendar.html` is a browser simulator that reads `.build/pages/` and mirrors the firmware's button logic (settle, browse timeout, month view, today block via an SVG color matrix). Keep it in step when that logic changes.
- Enclosure: `enclosure/calendar_frame.scad` (OpenSCAD, parametric). Panel outline 170.2 x 111.2 x 0.91 mm is measured; active area, FPC position, board sizes and the top-edge button module (seven keys, about 150 mm wide; the firmware uses three) are placeholders listed in `docs/enclosure.md`. `enclosure/build_viewer.py` exports the STLs and builds the committed, self-contained three.js viewer `enclosure/viewer.html` from `enclosure/viewer_template.html` (regenerate it after model changes) (OpenSCAD snapshot cask; the stable cask is disabled). The model renders without errors but has not been printed.
- Tests: `python3 -m unittest discover -s scripts`.
